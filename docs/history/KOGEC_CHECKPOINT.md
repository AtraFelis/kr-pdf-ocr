# KoGEC 공개 가중치·실행 조건 확인과 제한된 진단

날짜: 2026-10-13. 기존 문자 교정 평가 PR #10에 누적한다. 앱의 자동 보정과 편집 동작은 변경하지 않았다.

## 출처·사용 조건

- [개발사 설명](https://blog-en.sionic.ai/ko-gec)이 연결하는 [600M](https://huggingface.co/sionic-ai/nllb-200-ko-gec-600M)·[3.3B](https://huggingface.co/sionic-ai/nllb-200-ko-gec-3.3B) 가중치를 확인하고 로컬에 받았다. 실제 문서·OCR 결과를 온라인 서비스에 전송하지 않았다.
- 고정 리비전: 600M `a85a3e39efbcbf647866f681e74140fd293b9338`, 3.3B `413b34e43ffe8c7c5c431d9eb843e7102b0c994d`. 저장소의 가중치는 각각 약 2.46GB·13.38GB다.
- 3.3B 모델 카드의 라이선스 표기는 CC-BY-NC-4.0이다. 600M은 모델 카드·독립 라이선스 표기가 없고 기반 NLLB에도 비상업 조건이 있다. 일반적인 제품·상업 배포가 가능한 모델이라고 간주하지 않고 로컬 평가 전용으로 보관한다.

## 재현 조건의 불일치

[논문](https://aclanthology.org/2024.paclic-1.16.pdf)은 입력 `kor_Hang`과 교정 출력 `cor_Hang`을 설명한다. 개발사 블로그는 `ko_Hang`·`co_Hang`으로 표기한다. 공개된 두 모델의 토크나이저에서는 `kor_Hang`만 확인되고 다른 표기는 어휘에 없다. 둘 다 모델 어휘 크기 256206, 토크나이저 길이 256204로 두 ID에 해당하는 문자열 매핑을 공개 토크나이저에서 확인하지 못했다. 여유 임베딩 슬롯일 가능성도 배제하지 못하므로 가중치 손상을 단정하지 않는다. 현재 제공된 파일·설명만으로 학습 시 교정 토큰의 ID를 확정하지 못했다.

누락 ID를 임의로 추가하거나 임베딩을 새로 만들어 논문 결과를 재현했다고 표현하지 않는다. 조건 확인 도구는 `--diagnostic-only`를 명시한 한국어→한국어 제어 조건만 허용하고 결과에 `official_quality_evaluation=false`를 기록한다. 미매핑 출력 토큰·빈 후보·잘린 출력은 실패로 거부한다. 공개 파일 정합성 문제와 모델 자체의 성능 부족을 구분한다.

## 자료·실행

기존 합성 20개에 OCR 오류 형태를 반영해 직접 작성한 합성 10개를 추가했다. 사용자 문서의 저장 원시 JSON에서 짧은 대사 오류 2개를 골라 원본 페이지 PNG와 직접 대조한 정답을 만들었다. 실제 사례와 경로는 `output/kogec-input-01/cases.json`에만 저장하며 Git에 추가하지 않는다. 합성 30개와 실제 2개를 합친 32개는 대표 OCR 오류 전체를 평가한 자료가 아니다.

기존 `.venv`와 Transformers 내장 M2M100·NLLB 토크나이저를 사용했다. 패키지·잠금 파일은 바꾸지 않았다. Windows 11·RTX 5070에서 600M은 FP32, 3.3B는 FP16이며 로컬 가중치·토크나이저만 로드했다. 누락·불일치 가중치 없이 로드했고 실제 입력의 첫 토큰이 `kor_Hang`인 것을 확인했다. 입력 128토큰 상한, 빔 4, 최대 새 토큰 128개, 샘플링 없음, 출력 첫 언어 토큰은 알려진 `kor_Hang`으로 고정했다. 교정용 출력 토큰을 사용한 논문 방식과 다르다.

## 진단 결과와 해석 제한

모든 32개에서 두 모델의 후보를 생성했지만 이것은 정답 32개를 회복했다는 뜻이 아니다. 아래 수치는 한국어→한국어 조건의 진단 결과이며 논문 재현·모델 순위·도입 정확도로 사용할 수 없다.

- 600M: 원문 입력·Kiwi 후 입력 모두 정확 일치 6/32. 정상 13개 중 11개를 변경했다.
- 3.3B: 원문 입력·Kiwi 후 입력 모두 정확 일치 20/32. 정상 13개 중 각각 2개·4개를 변경했다.
- 3.3B가 일부 공백·마침표를 개선했지만 `훌륨한`을 그대로 두거나 `대단한`·`굉장한`으로 의역하는 후보도 있었다. 고유명사 표기 손실과 말줄임표 변경도 확인했다. 실제 짧은 대사 2개는 정답과 일치하지 않았다.
- 시간·RSS/CUDA 사용도 기록했으나 두 모델의 크기·정밀도가 다르고 반복 벤치마크가 아니므로 속도·품질의 일반적인 우열을 결론 내리지 않는다. 600M 초기화/전체 측정 구간 약 8.14/14.70초, 3.3B 약 11.45/21.30초. 모델과 Kiwi를 함께 로드한 RSS 관찰 최댓값은 약 3341/23063MiB, CUDA 최대 할당은 약 2393/6435MiB다.

기록은 `output/kogec-600m-probe-02/`, `output/kogec-33b-probe-01/`에 있다. 합성 20개만 실행한 초기 600M 결과는 `output/kogec-600m-probe-01/`로 구분한다. 기존 OCR JSON·PNG·편집본은 수정하지 않았다. 평가 스크립트는 Python 소켓 연결을 차단했고 OS 방화벽 검증·CPU 실행·장문·모든 실패 경로는 평가하지 않았다.

## 판단과 다음 단계

**공식 교정 토큰 매핑 확인 전 KoGEC의 정식 품질 평가·앱 도입은 보류한다.** 제한된 진단의 개선 사례만으로 도입하지 않고, 의역·고유명사 손상 때문에 자동 치환도 연결하지 않는다. 공개 배포자가 제공한 올바른 토크나이저·토큰 ID·추론 설정을 확보하면 같은 자료로 다시 평가한다. 작성자에게 문의하거나 문서를 외부에 보내는 작업은 수행하지 않았다.

합성 자료 확대와 실제 오류 2개의 이미지 대조는 완료했으며 다양한 오자·고유명사·장문 정답은 추가 확보해야 한다. 확인 가능한 교정 후보가 마련될 때까지 기존 PP-OCRv5·Kiwi·사용자 사전·원본 영역 VLM 재인식을 유지한다. 후속 제품 개발은 보정 제외 이유 표시·정상 영역 부분 복원으로 이어갈 수 있다.

## 코드·문서 확인

두 모델의 GPU 진단 실행 외에 Python 44개 Docstring·Ruff·포맷·Git 공백 검사를 통과했고 Markdown 34개에서 코드 예제 밖 로컬 링크 대상 169개를 확인했다. 진단 CLI 도움말을 실행했다. 별도 pytest 회귀 검사는 추가·실행하지 않았으며 등록된 과거 테스트 통과를 이번 변경의 결과로 사용하지 않는다.
